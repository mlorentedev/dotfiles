## `cli/` — standard Go CLI layout

Community-standard shape (go.dev module layout; same pattern as `gh` and `chezmoi`):

```text
cli/
├── cmd/dotf/
│   └── main.go          # entrypoint ONLY: version var (goreleaser ldflags) + cmd.New(version)
├── internal/
│   ├── cmd/             # Cobra wiring: one <verb>.go per subcommand (+ tests)
│   └── review/          # domain logic per subcommand family
├── go.mod               # own module — binary tags = releases, isolated from repo root
├── .goreleaser.yaml
└── README.md
```

Rules:

- `cmd/dotf/` never grows beyond `main.go` — the anti-flat-`scripts/` guard. `var version`
  stays there because goreleaser injects `-X main.version`; moving it breaks releases silently.
- Every future twin port lands as `internal/cmd/<verb>.go` + `internal/<domain>/`.
- The per-script migration map (which twin becomes which subcommand) lives in epic
  [#131](https://github.com/mlorentedev/dotfiles/issues/131) — single source, not duplicated here.

## Runtime data flow

What triggers what, once setup has already deployed the repo. Corrects the pre-ADR-028
assumption that secrets populate the shell environment at login — they don't; secrets are
injected per-child-process, on demand, and everything else is either structural env vars
(no secrets) or an explicit `dotf` invocation.

```mermaid
flowchart LR
    classDef trigger fill:#fee2e2,stroke:#dc2626,color:#000
    classDef hook fill:#dcfce7,stroke:#15803d,color:#000
    classDef sink fill:#f3e8ff,stroke:#7e22ce,color:#000

    NS([New shell]):::trigger --> RC[".zshrc/.bashrc<br/>source ~/.dotfiles/paths.sh"]:::hook --> ENV["structural env vars<br/>(ADR-025 — no secrets)"]:::sink
    CS([New agent session]):::trigger --> MEM["dotf mem session-start<br/>(session-start-config.json)"]:::hook --> CTX["additionalContext"]:::sink
    CMD([Secret needed]):::trigger --> SEC["dotf secrets run -- cmd"]:::hook --> CHILD["child process env only"]:::sink
    TIMER([Daily systemd timer /<br/>Scheduled Task]):::trigger --> UPD["dotf update<br/>(ff-only + setup)"]:::hook --> DEPLOY["~/.dotfiles converged"]:::sink
    PR([PR opened]):::trigger --> GATE{"spec-gate.yml<br/>discipline gate"}:::hook
    GATE -- "spec folder present,<br/>or skip-sdd + rationale" --> PASS["CI green"]:::sink
    GATE -- "neither" --> FAIL["CI red"]:::sink
```

## hive install model

hive (the `hive-vault` package) is a catalog tool. It has one pin, `packages.json`'s `version`, and
`dotf tools install` (converge's `tools` step) is the only thing that installs or upgrades it. The
OS decides the mechanism, not the owner of each machine:

| | Linux, macOS | Windows |
|---|---|---|
| Who owns the layout | uv (`uv tool`), ADR-036 | hive itself: `versions/<v>`, a `current` junction under `%LOCALAPPDATA%\hive\runtime`, and its launcher `%LOCALAPPDATA%\hive\bin\hive.cmd` (hive ADR-015, ADR-019) |
| What the catalog runs | `uv tool install --force --refresh-package hive-vault [--python <series>] hive-vault==<pin>` | `uv tool run --refresh-package hive-vault --no-build-package cryptography --from hive-vault==<pin> [--python <series>] hive self-upgrade <pin>`: the `self_install` field, ADR-036 amendment 2026-10-21. Nothing stays in uv's tool dir |
| When it runs | below the pin, or absent, probed on PATH | the same, probed on the process PATH and then the registered per-user PATH, so a hive newer than the pin is never `self-upgrade`d down |
| Daemon | `hive service install` from setup, a `systemd --user` unit; this repo owns only the drop-in `systemd/hive.service.d/` | `hive service install` from setup, a Scheduled Task |

**Upgrades are a pin raise, nothing else.** Nothing upgrades hive on a schedule or on hive's own
initiative (hive ADR-020: hive notifies, the owner applies). A new version reaches a machine when
`packages.json`'s pin moves and converge runs. The 15-minute timers that did this before
(`hive-upgrade.timer`, the `DotfilesHiveUpgrade` task) are deleted. The `hive-upgrade-retire`
converge step (`cli/internal/converge/hiveupgrade.go`) removes them from a machine that still has
them, and a second run changes nothing.

**A missing hive is the tools step's to report.** `dotf doctor`'s hive-daemon section names
`dotf tools install hive` as the fix on every OS. On Windows, a `uv tool` copy of `hive-vault` is
the layout ADR-019 rules out. It appears when a dotf older than the catalog's `self_install` field
(0.77.0 and earlier) converges this catalog (#1675). Recovering such a machine is #2991.

The decision trail is `specs/AI-028-hive-install-model-migration/` (#791).

# Lesson 205: Redact at the producer, because the consumer's filter is a guess about a format you have not seen

**Context**: diagnosing BUG-082 (`bw serve` returning a non-JSON envelope under batch reads) required seeing what the daemon actually replies with, because the client discards the body it fails to parse and reports only the offending character. Earlier probes in the same session had been careful — printing value *lengths*, HTTP status codes, and sha256 fingerprints, never the values themselves — and each of those answered its question without exposing anything.

**Problem**: the diagnostic step dumped raw response bodies through a `sed` redaction filter written against the *expected* shape. The real payload did not match that shape, the filter passed it through unchanged, and twelve full vault item bodies landed in the session transcript: a live DockerHub PAT, a second PAT stored in the `password` field, two plaintext entries from `passwordHistory`, and the item's encryption key. The local files were shredded immediately; the transcript could not be. The credentials had to be revoked and rotated, which is how the rest of the session's work on rotation came to be exercised for real. The redaction was not skipped — it was *present and ineffective*, which is worse, because it produced the confidence of having handled the problem.

**Solution**: extract structure at the producer instead of filtering at the consumer. Every subsequent probe parsed the JSON and emitted only derived facts — field *names*, value *lengths*, 12-hex-character sha256 prefixes — so no code path could emit a secret even if the payload had an unexpected shape. That is also what made the later verification possible at all: comparing fingerprints proved a credential had actually been replaced, which a liveness probe cannot do (an unrevoked old credential authenticates exactly as well as a new one).

**Rule**: never pipe a secret-bearing payload through a redaction filter and print the result. A filter is an assertion about a format you are debugging *precisely because you do not understand it*, and it fails open — the unmatched case is emitted verbatim, silently. Print only values you constructed yourself from parsed fields: a name, a length, a hash prefix, a boolean. When you genuinely need the raw bytes, write them to a 0600 file and inspect them with code that cannot reach stdout. And prefer a fingerprint to a value everywhere it will do — `sha256 | cut -c1-12` is non-reversible, is enough to prove two things differ, and turns "did the rotation work?" from a judgement into a comparison.

**Recurrence [2026-08-15, same day]**: it happened again, in the same investigation, by a simpler route — and the recurrence is the more useful half of this entry. Diagnosing BUG-082 still requires seeing what the daemon replies, so the probe was `curl -s "$BASE/object/item/$ID"`, which prints a vault item's `fields[].value` directly. No filter was involved, so the rule as written above — *"never pipe a payload through a redaction filter"* — did not cover it: the failure mode was one step **simpler** than the one that had just been written down. A live `NAN_API_KEY` was exposed and had to be rotated.

The lesson about the lesson: the rule was already written, already correct, and already read by the person who broke it, hours later. **The gap was never knowledge — it is that nothing made the safe path the easy one.** Probing a secrets-bearing endpoint is a legitimate and recurring need when the backend itself is the bug, and the only tool at hand (`curl`) prints the credential by default. Prose loses to convenience every time; a rule with no mechanical guard is a rule that documents the next incident rather than preventing it. Tracked as CLI-038 (#1012): a `dotf secrets probe` that reports status, shape, field names, lengths and `sha256[:12]` fingerprints, and structurally cannot print a 2xx body. Generalises past secrets: when you catch yourself writing a *stronger warning* for a rule that was just violated, the honest reading is that the rule needs a guard, not more words.

**Resolution [2026-08-16]**: the guard shipped. **`dotf secrets probe <id>` is the sanctioned way to ask what the secrets backend replied** — status, content-type, size, envelope validity, field names, value lengths and `sha256[:12]` fingerprints, and no field in its report type is capable of holding a value. `--raw` echoes a body only for a NON-2xx status, enforced in the reporting code rather than at the call site, because a 200 from `/object/item/<id>` *is* the credential. **Use it instead of `curl` for anything touching a secrets endpoint**; the interim `curl` recipe below it is now only for endpoints `probe` does not cover.

Two things it proved immediately, both of which are the argument for building instruments rather than writing rules. First, on its first live run it compared a stored fingerprint against a leaked one and found them identical — a credential reported as rotated had not been rotated in either store, and **a liveness check would have reported success**, since an unrevoked old credential authenticates exactly as well as a new one. Only "did it change?" catches that, and answering it used to require printing the value. Second, probing the new command with the inputs meaning *do nothing* found two defects in the tool itself: `--count 0` exited 0 having done nothing, and `--raw --count N` silently ignored `--raw`. The reusable half: **the happy path gets written and tested first, so the branches where nothing happens are the ones nobody looks at** — the same shape as a doctor check whose only reachable branch is its no-op one.

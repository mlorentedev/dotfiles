# CLI-011-release-please

> **Naming**: file lives at `<repo>/specs/CLI-011-release-please/proposal.md`. Implements the chosen approach for issue #369 (single-source version reconciliation).

## Why

<!-- from issue #369: CLI-011: adopt release-please (version + CHANGELOG + tag automation, single-source) -->

Cutting a release today is three manual, drift-prone steps with no single source of version truth: a human decides the next version, types `git tag vX.Y.Z` by hand, and opens a separate PR to bump `DOTF_VERSION` in `versions.conf` (PR #412 for v0.3.0 is the latest instance) — while `CHANGELOG.md` is regenerated by `scripts/changelog-gen.sh`, a tool that is **not wired into CI or setup** and so only runs if someone remembers. "What version is this?" lives in three places (the git tag, `versions.conf`, the changelog) that can disagree, and the version *decision* is a manual judgement call instead of being derived from the commit history. #369 asks for one source of version truth driven by Conventional Commits.

## What

Adopt [release-please](https://github.com/googleapis/release-please) as the version/changelog/tag authority, composed with the existing goreleaser build/publish. After this PR: landing Conventional Commits on `main` makes release-please maintain a standing **release PR** that, when a human merges it, (a) computes the next semver from commit types (`feat`→minor, `fix`→patch, `feat!`/`BREAKING CHANGE`→major), (b) regenerates `CHANGELOG.md`, (c) updates `DOTF_VERSION` in `versions.conf`, and (d) creates the `v${version}` git tag. That tag triggers the **unchanged** goreleaser `release` job in `cli.yml`, which builds and publishes the binaries exactly as it does now. Division of labour: **release-please = decide version + changelog + tag; goreleaser = build + publish**. Nobody types `git tag` or hand-bumps `versions.conf` again; the deliberate human gate moves from "push a tag" to "merge the release PR" (consistent with the repo's no-auto-merge rule).

## Out of scope

- **goreleaser itself** — `cli/.goreleaser.yaml` and the `release` job stay as-is; this PR only changes what *creates the tag*.
- **Re-releasing v0.1.0–v0.3.0** — release-please seeds at the current version and proposes the *next* one; published releases are untouched.
- **Conventional-Commit enforcement (commitlint)** — the repo already follows the convention by discipline; a CI linter for it is a separate ticket (note R6).
- **Artifact signing / SLSA provenance** — release hardening is a follow-up, not this PR.
- **Per-PR token convention (OPS-007 / #321)** — this PR consumes a release token; defining the broader per-purpose PAT policy is that ticket's job.

## Risks / open questions

- **R1 — `GITHUB_TOKEN` will NOT trigger goreleaser (the make-or-break risk).** A tag (or commit) pushed by a workflow using the default `GITHUB_TOKEN` does **not** trigger further workflow runs (GitHub's recursion guard). So if release-please creates the `v*` tag with `GITHUB_TOKEN`, the `cli.yml` `tags: v*` trigger — and thus the whole release build — **silently never fires**. **Mitigation:** run the release-please action with a **PAT** (fine-grained, `contents: write` + `pull-requests: write`) stored as a repo Actions secret; its tag push then triggers `cli.yml`. This is a hard dependency on the user provisioning that secret (ties into OPS-007/#321). Alternative considered + rejected: have release-please run goreleaser directly (couples the two tools, duplicates the existing job).
- **R2 — tag format must stay exactly `v${version}`.** `cli.yml` matches `tags: v*` and goreleaser derives `.Version` from it. release-please must emit `v0.4.0`, not `cli-v0.4.0`. **Mitigation:** single root package, `include-component-in-tag: false`, `tag-separator` unused.
- **R3 — `versions.conf` updater.** release-please must bump only the `DOTF_VERSION=` line. **Mitigation:** `extra-files` with the `generic` updater + an `x-release-please-version` marker comment on that line.
- **R4 — first-run bootstrapping.** `.release-please-manifest.json` must be seeded with the current `0.3.0` so the first release PR proposes `0.4.0` (not `1.0.0` or `0.1.0`). **Mitigation:** commit the manifest seeded at `0.3.0`.
- **R5 — retiring `changelog-gen.sh`.** Removing the script + its bats must leave no dangling references. `grep` confirms it is not wired into CI/setup; `CLAUDE.md` documents it (must be updated). The `architecture-md.bats` / docs guards must stay green.
- **R6 — Conventional-Commit dependency.** Non-conventional commit subjects are not categorised by release-please (land under "Other" or are ignored). Acceptable; enforcement deferred (see Out of scope).

## Acceptance criteria

Observable outcomes. Each must be testable.

- [ ] **AC1** — `release-please-config.json` + `.release-please-manifest.json` (seeded at `0.3.0`) exist and validate as JSON; a `release-please.yml` workflow triggers on push to `main`. *Verify:* `jq` parse + workflow yaml lint.
- [ ] **AC2** — release-please is configured single-root with `include-component-in-tag: false` so the produced tag is `v${version}`. *Verify:* config assertion (jq) + documented dry-run.
- [ ] **AC3** — the release PR updates BOTH `CHANGELOG.md` and the `DOTF_VERSION=` line in `versions.conf`. *Verify:* `extra-files` config asserts `versions.conf`; observed on the first real release PR (recorded in verification.md).
- [ ] **AC4** — the tag release-please creates triggers the existing goreleaser `release` job and publishes binaries (i.e. R1 token wiring is correct). *Verify:* observed end-to-end on first release; the workflow uses a PAT secret, asserted by grep on `release-please.yml`.
- [ ] **AC5** — `scripts/changelog-gen.sh` and `tests/changelog-gen.bats` are removed, `CLAUDE.md` no longer references the script, and the full bats suite + `architecture-md.bats` stay green. *Verify:* `grep -r changelog-gen` is empty (outside this spec) + `bats tests/`.
- [ ] **AC6** — `versions.conf` remains the single `DOTF_VERSION` source and is updated by release-please, not by hand. *Verify:* no manual-bump step in any runbook; `extra-files` covers it.

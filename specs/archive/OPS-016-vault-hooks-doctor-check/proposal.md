# OPS-016-vault-hooks-doctor-check

> **Naming**: file lives at `<repo>/specs/OPS-016-vault-hooks-doctor-check/proposal.md`. `OPS-016-vault-hooks-doctor-check` is `AREA-NNN-slug`.

## Why

<!-- from issue #549: OPS-016: Install knowledge-vault git hooks (pre-commit + pre-push) in dotfiles bootstrap -->

The knowledge vault enforces its secret gate with **local git hooks, never CI** — obsidian-git auto-pushes the vault on a timer, so a push-triggered pipeline would run almost continuously (the vault's `feedback-no-ci-for-vault` rule). gitleaks runs at `pre-push`. But `.git/hooks/` is not version-controlled, so a fresh clone has **no gate** until `pre-commit install` runs — and on 2026-06-23 the server-side backstop was removed (knowledge#114), leaving that manual step the only protection. The result is a silent secret-exposure gap on every new machine. dotfiles owns cross-machine provisioning, so closing the gap belongs here.

## What

`dotf doctor` gains a **`checkVaultHooks`** diagnostic (a new "Knowledge vault hooks (secret gate)" section). It verifies the vault's `pre-commit` + `pre-push` hooks are installed and pre-commit-managed; under `--fix` it provisions them by running `pre-commit install --hook-type pre-commit --hook-type pre-push` in the vault. It mirrors the existing `checkGuardHooks` contract: verify always, repair only under `--fix`, idempotent, safety-first. Provisioning is pure behavior (no repo asset to deploy), so it lives in the consolidated CLI checker rather than a new bootstrap shell script.

## Out of scope

- **Auto-running `dotf doctor --fix` from the bootstrap.** The bootstrap stays report-only (it runs plain `dotf doctor`), same contract as the GUARD hooks. Whether bootstrap should end with `--fix` (auto-provisioning this + GUARD wiring + the junction/env repairs at once) is a broader, all-checks decision tracked with HARNESS-040 (#551).
- **Installing the `pre-commit` tool itself.** A missing `pre-commit` is reported loudly; bootstrapping the Python tool is `checkCoreTools`/`checkOptionalTools` territory.
- **Windows production wiring of `dotf doctor`.** The check is cross-OS Go (and tested on the cross-OS matrix); the Windows doctor entrypoint is deferred per the package note.

## Risks / open questions

- **AC "installed right after bootstrap" vs report-only bootstrap.** Resolved (decision A): the gate is provisioned by `dotf doctor --fix`, matching GUARD; the bootstrap-auto-fix question rides with #551. No silent regression — a fresh machine's missing gate is surfaced as a `FAIL` by the bootstrap's `dotf doctor` run.
- **Hook detection keys on the `generated by pre-commit` marker.** A future pre-commit could change that string. Low risk — the marker has been stable across pre-commit releases — and a marker miss fails safe (reports the gate as missing, never a false PASS).

## Acceptance criteria

Observable outcomes. Each must be testable.

- [ ] **AC1** When both vault hooks are installed and pre-commit-managed, the section PASSES (no mutation).
- [ ] **AC2** When the gate is missing and `--fix` is NOT set, the section FAILS with remediation and performs no install.
- [ ] **AC3** Under `--fix` with `pre-commit` on PATH, both hooks are installed via `pre-commit install --hook-type pre-commit --hook-type pre-push` in the vault; a re-run is idempotent (PASS, no reinstall).
- [ ] **AC4** Under `--fix` with the vault present but `pre-commit` absent, the section FAILS loudly — never a silent skip.
- [ ] **AC5** When no vault checkout exists at the resolved path, the section SKIPS (non-fatal).
- [ ] **AC6** The vault path is resolved via the `VAULT_PATH` seam (no hardcode), reusing `checkVault`'s resolution.
